# Repository Guidelines

## Non-Negotiable Agent Workflow
- **Never run tests, test suites, test commands, or test-related validation unless the user explicitly asks for tests in the current turn.** A request to fix, implement, verify, or finish a change is not permission to run tests. Do not propose that tests be run; the user runs them independently.
- After every completed code, configuration, documentation, or workflow change, end the final response with exactly `Proponowana nazwa commitu: <short English subject>`.
- Always provide that proposed commit subject, even when no tests were run. Never create the commit unless the user explicitly requests it.
- Respond in Polish and report only validation actually performed.

## Project Structure & Module Organization
This is a Python/FastAPI multiplayer TTRPG application with Gemini narration and generated illustrations.
- `app/main.py`: FastAPI composition, middleware, static mounts, lifespan wiring, and domain-router registration.
- `app/api/routers/`: UI, auth, push, admin, session, character, turn, action, image, world-catalog, and chat/WebSocket route registration; keep public paths and response models stable.
- `app/services/`: extracted application behavior. `runtime.py` contains shared helpers and startup compatibility logic; focused services own sessions, characters, turns, proxy voting, chat, images, the read-only world catalog, push subscriptions, auth, admin, and UI responses. `ui_service.py` renders the pinned theme before frontend assets load.
- `app/services/room_access.py`: PBKDF2 room-password helpers and a signed cookie containing the authorized room code. Protected HTTP operations and WebSockets must verify that their session, character or turn belongs to that room. Room access is shared; there is no per-character account identity.
- `app/services/market_service.py` and `app/api/routers/market.py`: persisted post-battle market visit, generated merchant and stock, engine-owned prices, room-gated transactions, haggling, and hidden description-driven theft. The workshop uses existing turn crafting with persisted source item IDs. Market CSS/JS and `market_panel.html` use semantic theme tokens.
- `app/worlds/models.py`, `registry.py`, `recipes.py`, and `packs/`: frozen Pydantic `WorldPack` contracts for classes, ability books, controlled mechanics, loot/crafting, item vocabulary, encounters/status presentations, maps, lore, narration and theme; validated ID/version/reference lookup and immutable declarative JSON definitions. Two existing full JSON packs and 13 strict `recipe_v1` JSON packs materialize to the same complete contract at import. Registered packs total 15; `dark_fantasy@1` remains the zero-argument legacy fallback only for rows lacking both persisted world fields.
- `app/models.py`, `database.py`, and `schemas.py`: SQLAlchemy persistence and Pydantic contracts, including per-room password hashes, persisted scenario selection, pinned world-pack versions, stable class/ability IDs, controlled character narrative form, five character attributes, named world-lore entries with learned attacks and NPC traits, death state, character coins, controlled `active`/`on_break` participation with its starting turn, and the persistent per-campaign calendar-day image-generation quota. `database.py:init_db` additively fills missing required columns on direct local startup.
- `app/dice.py`, `combat.py`, `inventory.py`, `loot.py`, and `magic.py`: weighted narrative intent/stat interpretation, action-relevant equipment bonuses, server-side dice, pack-driven abilities and encounters, explicit self-relief from harmful statuses, targeted healing/protective support, death/stabilization/resurrection, equipment, loot/crafting, and legacy magic adapters.
- `app/targeting.py`: controlled extraction of a character attack target from the player's written declaration; attack UI has no target picker.
- `app/map_generator.py`: deterministic campaign-map generation from a pinned map profile and map serialization.
- `app/services/runtime.py`: engine-owned map movement resolves successful travel declarations to adjacent nodes independently of the narrator's requested destination; Gemini may update only the validated location chronicle. Visited edges take precedence over available-edge styling.
- `app/gemini_service.py`: structured Gemini narration, campaign setup, and generated scene images.
- `app/push_service.py` and `generate_vapid_keys.py`: Web Push delivery and VAPID setup.
- `app/websocket_manager.py`: real-time event and chat broadcasting.
- `app/templates/index.html`: document shell with server-rendered `data-theme`, semantic colors, theme meta, and ordered frontend assets; `app/templates/partials/` owns the auth gate, lobby, character selection, game-table panels, and individual accessible modals.
- `app/static/js/app.js` composes the single Alpine `rpgGame` component from feature objects in `app/static/js/modules/`; named local Alpine components own story-hint and attribute-info disclosure state.
- `app/static/css/style.css` is the cascade entrypoint for token, base, component, inventory, map, lore, feedback, responsive, semantic theme, and `theme-art.css` world-presentation modules under `app/static/css/modules/`; `app/static/js/theme-bootstrap.js` applies a vetted local preview/last-known pack theme before CSS and updates theme metadata. `app/static/sw.js` must precache every versioned local frontend module. The document uses a versioned 32×32 PNG favicon plus SVG fallback; the PWA manifest and icon URLs are versioned so browser and installed-app icons can refresh after deployment. Keep their URLs and service-worker precache entries synchronized when changing icon assets.
- `app/static/img/merchants/`: app-owned transparent PNG standing-merchant art keyed by validated `theme_id` for all 15 worlds. The market component loads the pinned campaign theme's local image and falls back to an icon if unavailable. Supplied replacement art belongs here, not in immutable world packs or generated-scene uploads.
- `tests/`: dice, combat, loot/crafting, API, lobby/admin, full turn resolution, WebSocket chat, current-world/frontend contracts, world-registry validation, synthetic stage-6 pack, stage-7 theme/selection, stage-8 NeoKatowice pilot, stage-9 world recipes/maps/books, and isolated Alembic migration coverage. `tests/conftest.py` binds lobby, turn, full-resolution and WebSocket integration tests to a disposable SQLite campaign pinned to `dark_fantasy@1`, including direct chat and push session factories.

- `uploads/`: generated images; `data/`: Docker-mounted SQLite storage.

## Current Feature Baseline
The server supports multiple simultaneous code-addressed rooms with independent PBKDF2 passwords, GM-PIN room creation with world/scenario/tone selection, room-bound HTTP/WebSocket access, room-specific push links and isolated campaign state. The selected scenario is persisted from the first lobby. Character creation stores a controlled `masculine`/`feminine`/`neutral` narrative form that affects narration only; Gemini must not infer it from name or class, and historical characters default to `neutral`. The existing `kampania-1` and all dependent data remain unchanged; on its first successful login it adopts the configured legacy `ROOM_PASSWORD` as a PBKDF2 hash. The browser remembers only the last room code, not the room password. A single browser profile holds one active room cookie at a time; switching rooms replaces that cookie without affecting either campaign.

The maintained feature set includes room-password/GM-PIN access, lobby/readiness, reversible GM-controlled character breaks, server-side random d20 rolls, narrative-first weighted intent/stat recognition with player correction, levels to 25, equipment claims and limits, targeted support, downed/stable/dead states and resurrection, phase-based encounters with status effects, location/enemy loot and post-encounter crafting, a persistent zoomable campaign map, shared categorized lore, proxy-action voting, chat/notes, accessible responsive PWA panels, Web Push, automatic session/WebSocket resynchronization, and one on-demand scene image per campaign per `Europe/Warsaw` calendar day. The validated registry exposes 15 `d20_v1` worlds through `GET /api/worlds`: unchanged `dark_fantasy@1` and `neokatowice_3077@1`, plus 13 stage-9 packs covering pirate, desert, Slavic, WWII-occult, witch, western, Viking, space-grimdark, dark-action, pastoral, cosmic-horror, consulting-detective, and humorous-dungeon campaigns. Dark Fantasy remains the legacy default. Campaigns pin exact pack ID/version; characters persist `class_id`, actions persist `ability_id`, and legacy name/`magic_*`/`active_boss_*` fields remain compatibility adapters. The generic runtime reads class starters/quick actions/ability books, controlled mechanics, action-stat cues, item vocabulary, loot/crafting search markers and item-name exclusions, enemy/status/map/lore profiles, scenario prompts, narration, image direction, and offline text from the pinned pack. Its frontend gets class, action and map-icon content from API. The GM world selector applies only to the *next* campaign on an explicit confirmed reset; direct changes to active campaign state stay rejected. The server renders controlled pack colors/shape on the document root and theme metadata; frontend may show a local, persistent `neon_preview` without changing the saved world, and SW caches versioned theme assets. `theme-art.css` adds distinct typography, restrained textures, thin trim, and mobile shadow/heading adjustments for all 15 world themes without changing published pack data; the humorous dungeon uses comic lettering and a halftone pattern. Display fonts use Google Fonts with system fallbacks. The app identity uses a mathematically exact, multi-genre D20 icosahedron SVG logo and precached raster PWA icon suite (192, 512, maskable, apple-touch, favicon), integrated directly into the auth gate. NeoKatowice 3077 is a fictional cyberpunk Poland pilot with Hacker, Neurotechnician, Exo Guard and Fixer books, starter gear, Katowice sectors, loot, encounters and art direction; its angular theme uses controlled `cut_corner` shape while Dark Fantasy stays rounded. Perception is the fifth canonical attribute across ORM/API/creation/cards/lobby/level-up/GM/items/dice/Gemini; sensory awareness must stay distinct from intellectual analysis. Peaceful stage-9 packs disable only automatic offline enemy naming through a validated narrative-profile flag; GM-triggered encounters still work. Stages 6–8 were manually accepted; stage 9 awaits owner acceptance. Keep this baseline synchronized with implementation changes.

If every active character is incapacitated, the normal action gate is replaced by a GM crisis flow. Emergency retreat completes the blocked turn without AI, clears the active encounter, returns only `downed` or `stable` participating characters at 1 HP, clears harmful timed effects, and opens a recovery turn; dead and `on_break` characters are not revived or changed. Completed turns expose deterministic status-damage, boss-hit and defence breakdowns in the mechanical event ledger even when generated prose omits them.

Turn resolution uses the backend as the sole authority for HP, XP, inventory, status transitions and map movement. Gemini receives the persisted outcome, exact engine-owned XP, relevant item-bonus sources and combat events, and may only narrate them; its structured HP/XP/item fields are normalized back to engine values before persistence. XP is fixed by outcome tier (`critical_success` 120, `success` 80, `partial_success` 60, `failure` 50, `critical_failure` 40). A successful action remains successful even when an independent status or enemy response also occurs, and the UI labels these separately as the action goal and the whole-turn HP balance.

Explicit attempts to extinguish `burning` or break free of `frozen` are defensive actions resolved before status ticking. Success removes the effect, partial success reduces it, and failure leaves it to tick; a later enemy event may apply a new effect. An unmentioned weapon or shield does not boost an unrelated roll, only one weapon contributes to an attack roll, and a weapon named in the declaration takes precedence. Ordinary non-healing support grants `guarded` rather than restoring HP; only healing intent or a `heal` mechanic heals, while `cleanse` removes controlled statuses without implicit healing.

Attribute fallback and dice totals treat an unset transient or historical ORM stat as `0`. Crafting treats an unflushed inventory `quantity` default as one item while still rejecting an explicit zero quantity; validation and consumption use the same normalization.

An `on_break` character preserves level, XP, HP, coins, inventory, learned abilities and timed status state. They are excluded from lobby/turn readiness, proxy voting, new encounter sizing, enemy/party targeting, support, status ticking, death progression, loot, market/workshop operations, automatic naming and Gemini/offline party context. Starting a break is rejected during turn resolution and removes that character's pending action and target proxy decision from the still-open turn; returning marks them `active` for the open turn. The lobby and in-game party list must label them `Na przerwie`, never `Czeka`, and an incapacitated character must be labelled by their death state rather than as waiting. The frontend must not expose proxy voting for either group. Encounter HP, armor and DC remain pinned when participation changes, while each boss response is capped to the attack count appropriate for the currently participating living party. Campaign reset restores every retained character to `active`; setup-scenario may still replace the roster according to its existing reset contract.

Written attacks can target a party character by name or, when exactly one other living character exists, a singular ally reference. The server persists the inferred character ID, applies d20-based damage and HP/death state, and emits `character_attack`; an ambiguous ally reference requires a name in the description. There is no attack target picker. Improvised thrown stones use smaller damage. Support can select the caster except for resurrection. Search is once per map node even on failure, has a 20% empty chance after a successful result, and awards any item and coins to the finder. Loot narration is reconciled against backend events. Random non-consumable loot may be cursed, with a primary bonus of at least +2 and a secondary −1 penalty active only while equipped. Before finishing, an unlocked GM can use `POST /api/session/generate-ending-draft` to start a non-persistent background job and poll it with `GET` to obtain a read-only whole-history summary, an editable definitive finale and a separate character epilogue without changing campaign state. The GM may select an automatic, victorious, bittersweet or tragic ending tone and provide optional guidance. The finale must resolve the main conflict without behaving like another turn; a draft ending in a question, containing a known continuation marker or exceeding a response-field limit gets one corrective generation. Any still-oversized prose is fitted locally to the public response limits while retaining its opening and final closure, so one ignored model limit does not fail the whole job. Long chronicles are summarized chronologically in large hierarchical chunks to limit Gemini request count, and Gemini calls do not block the application event loop. A GM can end an active campaign with a persisted combined finale and epilogue using `POST /api/session/finish-campaign`; completed campaigns show it and reject further action submission, proxy voting, or resolution. Published world packs are unchanged.

Encounter balance is engine owned. At creation, use living characters' equipped items, five attributes, d20 success tiers, and enemy armor/DC to estimate one attack per character and set enemy HP for roughly 3.5 rounds; use a smaller party-size floor for solo play. Persist the maximum response count in the encounter telegraph: one attack for 1–2 living characters, two for 3–4, three for 5 or more, with distinct targets and reduced solo damage. Do not recalculate established HP, armor or DC when the party changes, but cap each response and its display telegraph to the same 1/2/3 thresholds for the currently participating living party; old active encounters without `attack_count` retain a maximum of one attack. Noncombat turns persist `challenge_tier` as `standard`, `hard`, or `climactic`; the server computes DC 12, `min(25, 15 + average_level // 2)`, or `min(30, 18 + average_level // 2)`. Enemy defense and feature DC take priority during combat. Gemini supplies a controlled tier matching the next prompt; offline narration marks every third turn hard and every fifth climactic. Published world packs remain unchanged.

Both GM campaign restart paths (`setup-scenario` and `reset-campaign`) clear `NamedLoreEntity` rows for the room and pending naming state in the same database transaction as the reset. Existing lore is retained during an active campaign and during additive migration; do not carry named discoveries into the next scenario or Gemini's turn context.

Lore discoveries are campaign state, not pack content. Automatic attack naming requires a successful attack, a verbatim scene excerpt, turn 8 or later, and an eight-turn gap since the last named attack; the offline narrator can also propose one after a successful encounter hit. NPC naming also requires scene evidence; offline NPC naming is available through the GM tools. Manual GM naming remains available. The chosen living character owns the learned attack, which is selected separately from pack abilities and adds exactly one damage after armor on a successful or partial hit; it never stacks with a class ability. NPC lore stores first meeting map node, controlled disposition (`gentle`, `rough`, `vulgar`, `reserved`), optional goal and catchphrase. Pass persistent NPC identity to Gemini, but ask it to repeat catchphrases only occasionally. Keep the pending naming question, turn and map node across session refreshes; clear them on naming and both campaign restart paths. Existing lore and active campaigns survive additive migration.

The World Chronicle also contains a collapsed campaign-goal section with the main mission, current clue, and controlled `started`/`in_progress`/`near_resolution`/`completed` state. Build the mission only from the player-visible scenario, update the clue only from an already published turn prompt, and never expose hidden enemy data, future locations, or narrator-only context through this section.

Inventory has two hand slots, one armor slot, one helmet slot, one boots slot, and five active item slots. A two-handed weapon occupies both hands. The helmet appears above the silhouette's head and boots below its feet; hand-slot labels, item names, and bonuses wrap without clipping on mobile. Helmet and boots are controlled item types with at most +1 attribute bonus when granted by GM; existing published v1 loot tables are unchanged. Backpack items can be transferred immediately to a living character in the same room, including a chosen count from a stack; transfers are blocked while a turn resolves and use an atomic owner/quantity update. The shared room cookie proves room access, not character ownership. Characters hold nonnegative integer coins separately from inventory stacks; the recipient of a boss or exploration loot drop also receives an engine-calculated coin reward, and the GM may adjust balances. After a boss defeat, the next turn always offers the workshop and has a 60% chance of a named merchant. The GM can open a merchant post manually between encounters. A post remains anchored to the location where it opened for at most three turns and closes earlier after successful map movement leaves that node. The visit, offers, stock, one haggling attempt per character and one hidden theft attempt per character persist through refreshes; purchase, sale, discounts and theft outcomes are server-owned. Caught theft fines up to available coins and bars the character from the current and next merchant visit. A player describes theft and names one offered item; the UI never advertises a theft button. The merchant is added to NPC lore, and being caught changes their disposition. Workshop selection passes three item IDs with the turn action and consumes them only on a successful craft. Scenario setup and campaign reset clear market state. The shop is available within an active campaign because setup-scenario deletes characters and their wallets. The Dark Fantasy equipment silhouette stays fantasy, NeoKatowice and its local preview use a cyber silhouette, Norki use a pastoral silhouette, and other themes use a softened neutral silhouette. Keep CSS art choices in app-owned files, not published packs.

The market card shows one standing merchant illustration per pinned world theme. Filenames are the theme IDs with `.png`, including `neo_katowice.png` for the `neokatowice_3077` pack. Merchant personas must use the app-owned grammatical-form pool matching the corresponding portrait. Keep these images local, decorative, and small-screen readable; do not add external asset URLs or art fields to published packs. When replacing an image, bump its URL version in `market.js`, the module and CSS versions in `index.html` and `style.css` if modified, and the service-worker cache name and exact precache paths for changed frontend modules. Scene images in `uploads/` are separate from these static merchant portraits.

## Build, Test, and Development Commands
Use Python 3.11+ locally; Docker uses Python 3.12. Run commands from the repository root.
- `python -m venv .venv`: create a virtual environment; activate it in PowerShell with `.\.venv\Scripts\Activate.ps1`.
- `python -m pip install -r requirements.txt`: install application and testing dependencies.
- `Copy-Item .env.example .env`: initialize local configuration if `.env` does not exist.
- `python -m alembic upgrade head`: migrate the configured database after taking a backup of any active SQLite campaign.
- `python -m uvicorn app.main:app --reload --port 8000`: start the development server.
- `docker compose up -d --build`: build and start the container.

There is no separate frontend build step.

Direct local Uvicorn startup uses `app/database.py:init_db` as a compatibility fallback for historical databases without Alembic revision tracking. Keep the fallback aligned with additive required columns such as `characters.coins`; otherwise ORM reads in startup lifespan fail before the app opens. Alembic remains the authoritative migration path.

## Coding Style & Naming Conventions
Follow surrounding code: four-space Python indentation, `snake_case` functions and modules, `PascalCase` classes, and uppercase configuration constants. Preserve existing JavaScript naming and indentation. Use type annotations for backend interfaces and Pydantic models for structured payloads. Keep database access asynchronous. No formatter or linter is currently configured.

## Testing Guidelines
Tests use pytest, pytest-asyncio, and HTTPX ASGI clients. Name files `test_*.py` and functions `test_<behavior>`. Intent/stat tests cover ambiguous prose, including incidental shouts and defensive words used inside offensive declarations. No coverage threshold is configured. The suite command, for the maintainer's reference, is `python -m pytest tests/`. Lobby, turn-flow, full-resolution and WebSocket chat tests must depend on `isolated_dark_fantasy_db`; it patches API, direct `get_db`, chat and push access to a temporary SQLite file and must never touch the configured campaign database. Other integration or acceptance checks also require an isolated database or copy.

`tests/test_encounter_difficulty.py` covers party-size response count, distinct targets, expected-damage scaling, and DC precedence. Balance acceptance checks belong on an isolated database or copy, including solo and four-player encounters and high-level noncombat challenges.

`tests/test_character_targets.py` covers a written party target, an ambiguous ally reference, mechanical party damage, and self-healing. `tests/test_loot.py` covers the finder receiving loot, a successful search of an empty room, stripping an unawarded artifact from narration, and equipped curse modifiers. Keep migration and current-world route/event/session fixtures synchronized with the campaign ending contract.

`tests/test_combat.py` also covers successful and failed extinguishing, including removal before status damage. `tests/test_dice.py` covers action-relevant equipment, one-weapon roll bonuses and precedence for a named weapon. `tests/test_character_targets.py` distinguishes ordinary protective support from actual healing. `tests/test_full_resolution.py` pins the engine-owned XP table.

Tests that deliberately reuse an existing turn must clear `resolved_at`, `mechanics_resolved_at`, and stale combat events before submitting a new action. Map assertions must resolve special nodes through `start_node_id` or `final_node_id`, because branch nodes are appended after the main path and list position is not a stable domain contract.

`tests/test_world_migration.py` creates an isolated legacy SQLite schema and invokes Alembic to verify additive backfills while preserving campaign progress. Migration tests must never point at `data/ttrpg_game.db` or another active campaign database.

WebSocket integration tests use a class valid for pinned `dark_fantasy@1`, consume an optional initial `CHAT_HISTORY` snapshot before asserting the newly broadcast `CHAT_MESSAGE`, and keep their chat session factory bound to the shared isolated fixture.

`tests/test_current_world_contract.py` is the compatibility gate for the staged multi-world refactor. Its route walker must continue to support FastAPI's lazily included routers. Update its fixture only for intentional public behavior changes. Backend/frontend moves must preserve the route table, WebSocket event names, current class starter sets, ability books, session shape, map profile, and UI markers recorded there. Consult `docs/WORLD_DEPENDENCY_INVENTORY.md` before moving world-specific behavior. Published world-pack versions described by ADR 0001 are immutable, declarative data and must not contain executable Python, JavaScript, arbitrary HTML/CSS, or untrusted external asset URLs.

Inventory and character-participation changes also update the relevant engine filters, session DTO, Alpine getters, GM controls, WebSocket refresh, versioned CSS/JS and service-worker precache. Do not turn helmet/boots into active accessories or retag historical items by name. Migration and manual state-changing acceptance belong on an isolated database or a copy of the campaign.

Market transactions require the signed room cookie and a living character in the same active session, but the cookie does not prove individual character ownership. Keep offer generation and prices on the server, bound stock to the persisted visit, atomically debit/credit coins with item changes, and use `market_revision` compare-and-swap when changing the visit. Theft is inferred only from explicit prose naming one current offer, never from a visible button; retries and sanctions are persisted. Shop and workshop remain available for at most three eligible turns, close when successful travel leaves their anchored map node, are unavailable during resolution or combat, and close on campaign completion or reset. Do not mutate published world packs to add shop content; offers use their validated loot vocabulary. The frontend market module must be versioned and precached with its CSS and the entrypoint.

World packs are loaded and fully validated when `app.worlds.registry` is imported. The 13 stage-9 `recipe_v1` JSON files are strict, frozen declarative shorthand expanded by `app/worlds/recipes.py` to a complete `WorldPack`; never bypass the final `WorldPack` validation or add world-ID-specific branches to the materializer. All collections in Pydantic models must remain tuples or frozen child models. Resolve explicit packs only by the complete `(id, version)` pair and fail closed for unknown values; the zero-argument lookup is the sole legacy fallback to `dark_fantasy@1`. New pack fields must use controlled schemas and mechanic keys rather than arbitrary mappings or executable behavior. Published pack IDs/versions and materialization rules are immutable; changing existing stage-9 recipe output requires a new version and migration plan.

Lore category IDs (`boss`, `location`, `npc`, `weapon`, `attack`) and all five attribute IDs are stable engine contracts; a pack changes their labels, not persistence IDs. `enemy_profile.lore_category_id` is `boss` until a versioned schema/API change. Only the published Dark Fantasy pack may use legacy `magic_*` compatibility fields as its primary display path; new pack logic uses `ability_book` and `ability_id`. Do not insert world-ID branches into routes, combat, or frontend content rendering. Stages 6–8 were accepted by the user; stage-9 per-world manual acceptance checklist is in `docs/WORLD_PACK_ROADMAP.md`.

Frontend refactors must preserve the property descriptors of the main Alpine component, rendered DOM selectors and accessibility attributes, CSS cascade order, and script initialization order. When adding or renaming a local JS/CSS module, bump its query-string version and the service-worker cache name, then include the exact versioned path in `PRECACHE_ASSETS`. There remains no separate frontend build step.

The turn-resolution button in `app/templates/partials/table/action_panel.html` stays above the collapsible action content and appears whenever all living players have submitted actions. Keep it visible in the compact sticky panel; hide it while a turn is resolving.

The map SVG must set the case-sensitive `viewBox` attribute so zoom and pan update visibly. Pan distance uses the rendered SVG scale with `preserveAspectRatio`; movement after a successful travel action stays on a legal adjacent node even if the narrator omits its destination. Previously visited links and doors use visited styling, including when they touch the current node.

Theme profiles must declare all thirteen `#RRGGBB` semantic token IDs and use only vetted presentation IDs: typography `classic`/`modern`, texture `runes`/`grid`/`none`, icon set `classic`/`neutral`, shape `rounded`/`cut_corner`. Do not interpolate arbitrary pack CSS, font URLs, image URLs, or scripts into HTML. `ui_service.py` must keep theme bootstrapping server-side; `theme-bootstrap.js` runs synchronously before CSS and maintains the last validated pack theme for offline navigation. The local Neon preview is device-only and must clear on a pack switch. `GET /api/worlds` is a safe catalog; only the GM-confirmed `setup-scenario` reset may use `allow_new_campaign_reset` to change a pack while discarding the old campaign. Direct pack changes on active campaigns stay blocked. NeoKatowice room icons are declarative text glyphs exposed in `map_room_icons`; the default pack keeps the old map-icon fallback. Pack-driven `ui_copy` supplies short lobby/selection text using Alpine `x-text`, never arbitrary HTML. Narrative named weapons use a controlled target stat; the default remains `strength`, NeoKatowice chooses `agility`. ## Commit & Pull Request Guidelines
History uses short English subjects such as `Images fix` and `app as a PWA`; no strict prefix convention is established. Write descriptive subjects focused on the change. PRs should explain behavior changes, reference relevant issues, and include screenshots for UI changes. Report only validation actually performed. At the end of every completed change, propose a short English commit subject to the user; do not create the commit unless explicitly requested.

## Security & Configuration
Keep secrets in `.env`; update `.env.example` when adding settings. Never commit credentials, SQLite databases, or generated uploads.

## Agent Instructions
Respond in Polish, concisely, as to an engineer. State concrete changes and relevant limitations without unnecessary explanation. Do not run tests or propose running them; the user runs tests independently unless explicitly requesting otherwise.

Treat documentation as part of every completed change. Before finishing any implementation, configuration, structure, command, or workflow change:
- update `README.md` so its feature list, setup instructions, configuration, project tree, and test inventory match the repository;
- update `AGENTS.md` with the corresponding repository guidance or current feature baseline;
- mention both documentation updates in the final summary;
- finish the final response with `Proponowana nazwa commitu: <short English subject>`.
